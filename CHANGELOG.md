## [Unreleased]

### Added

- Three new write/read tools close the gap where a queue created through `create-queue` had no way to be given a topic subscription without leaving the MCP tool set: `create-queue-subscription`, `delete-queue-subscription`, and `list-queue-subscriptions`. Without a subscription a queue attracts no messages regardless of its other settings, so `create-queue`'s description now names `create-queue-subscription` as the required follow-up rather than leaving the caller to discover the gap by failure. `create-queue-subscription`/`delete-queue-subscription` follow the flat-sub-resource-tool convention (one MCP tool per SEMP operation on the sub-resource, not a nested parameter on `create-queue`): a queue's subscriptions are added and removed over its lifetime, and the SEMPv2 create/delete operations for `MsgVpnQueueSubscription` take one topic at a time — there is no `update-queue-subscription`, since a subscription is immutable (SEMP has no update operation for it; changing one is delete-and-recreate). Both accept Solace wildcards (`>`, `*`) in `subscriptionTopic`, which can contain `/` — the first MCP tool parameter in this codebase to put an arbitrary, slash-bearing string into a SEMP path segment (`delete-queue-subscription`'s URL). `list-queue-subscriptions` verifies the queue exists before listing (a `monitor/getMsgVpnQueue` preflight step): SEMP's own collection GET returns `200` with an empty list for a nonexistent queue, which would otherwise be indistinguishable from "queue exists, has no subscriptions" — the preflight surfaces the broker's own not-found error instead. `delete-queue`'s description and confirmation preamble now state that deleting a queue also removes any subscriptions attached to it, since deleting a queue cascades to its subscriptions with no separate detach step and no error if it does. `delete-queue-subscription`'s own confirmation preamble likewise now states the silent-traffic-loss consequence in the restate clause itself (previously only in the description body, so the model wasn't instructed to say it back to the user before proceeding). Tracked under SOL-153868.
- Every release now publishes a CycloneDX SBOM (`solace-broker-mcp-<tag>.cdx.json`), generated by `cyclonedx-gomod` (pinned `v1.10.0`, matching this repo's Go version) against the same dependency closure `THIRD_PARTY_LICENSES.md` inventories, checksummed alongside the binary archives. A new `.github/scripts/sbom-check.sh` (with its own self-test, `sbom-check.test.sh`) verifies the SBOM's dependency set matches `THIRD_PARTY_LICENSES.md` before it's attached — resolving both sides to their Go module first, since the SBOM lists components at module granularity while the document lists some rows a package deeper (e.g. `golang.org/x/sys/cpu` inside module `golang.org/x/sys`), which a naive string comparison would misread as drift on every run. Per SOL-148440, the SBOM does not gate on its own absence — `cyclonedx-gomod` failing degrades the release to "no SBOM attached," never "no release" — but once an SBOM exists, a real divergence from `THIRD_PARTY_LICENSES.md` does fail the release, the same as any other compliance drift here.
- New `deploy/kubernetes/ingress.yaml.example`, and `docs/authentication.md` § "Session Routing at the Ingress" documenting it as a **required** step rather than a caveat. Now that the manifests default to `replicas: 2` (SOL-152089), an operator following the TLS-terminated-upstream pattern gets a deployment that fails on essentially the first call: an Ingress load-balances to pod IPs and so bypasses the Service's `sessionAffinity: ClientIP`, and MCP sessions live in a single pod's memory, so each call after initialize has roughly a `1/replicas` chance of reaching the pod that owns the session — a 10-call session survives with probability `(1/2)^10` ≈ 0.1%, and worse in practice, since nginx's default round-robin is deterministic rather than random. The working annotation is `nginx.ingress.kubernetes.io/upstream-hash-by: "$remote_addr"`, which restores at the ingress what `sessionAffinity: ClientIP` gave on the ClusterIP path, inheriting its NAT caveat. The docs now also name the two configurations that look correct and silently are not: cookie affinity, which needs a cookie jar no MCP client has, and hashing on `$http_mcp_session_id`, which fails because the initialize POST carries no such header — the server mints the ID onto the response, so that request hashes on an empty key and lands anywhere while the ID it returns hashes independently, stranding half of all sessions at two replicas. Gateway API's `sessionPersistence` fails for the same reason cookies do; controller-specific source-address hashing is the portable answer. The example routes the whole `/.well-known` prefix rather than just `/.well-known/oauth-protected-resource`, because clients probe several paths under it before they hold a token and the server answers the unregistered ones with a JSON 404 that nginx's plain-text default backend would otherwise replace; `/livez` and `/readyz` are deliberately left unexposed. Named `.example` so the directory-wide `kubectl apply` skips it. Documentation and example manifests only — no code change. Tracked under SOL-153834.
- New `THIRD_PARTY_CLASSIFICATION.md`: a committed green/yellow/red classification of every dependency in the shipped closure, sourced directly from FOSSA's policy result for `SolaceProducts_solace-broker-mcp` (Issues tab: zero active violations) rather than inferred from licence type alone. Zero dependencies are classified red, stated explicitly. The two MPL-2.0 dependencies (`github.com/hashicorp/go-cleanhttp`, `github.com/hashicorp/go-retryablehttp`) are classified yellow, per policy — see that file for approval status. Unlike the SBOM, this file is a committed snapshot, not a generated artifact — a yellow approval is a human decision that must survive a re-run. Tracked under SOL-153188.
- A Prometheus-format `/metrics` endpoint is now served on a dedicated listener (default `:9091`), separate from the main MCP port, so operators can apply an independent network policy to metrics scraping without changing MCP traffic rules. The capability is gated by the new `OBS_METRICS_ENABLED` environment flag and is **off by default** (v1 door-closing policy): when off, no second listener is started and no instruments are registered; when on, the listener is registered as a required `metrics_endpoint` readiness probe, so a bind failure (for example, the port already in use) surfaces on `/readyz` as `metrics_endpoint: <err>` instead of failing silently. The bind address is configurable through the new `observability.metrics_bind_address` YAML field (default `:9091`, `${VAR}` substitution supported). When metrics are enabled, config load now rejects a `metrics_bind_address` that shares the MCP server's own port — the two listeners would otherwise race for it at startup, and the loser, being a required readiness probe, would hold `/readyz` unready and crash-loop the pod; the guard is wildcard-aware (`""`, `0.0.0.0`, `::` overlap any host on the same port), and the `:9090`/`:9091` defaults never collide. The endpoint serves Go runtime and process collectors plus three self-observation instruments — `mcp_build_info{version}`, `mcp_schema_version{metrics_schema,audit_schema}`, and the `mcp_metrics_scrape_total` counter — on an OpenTelemetry meter provider that later metrics work registers additional instruments against; OpenMetrics exposition is enabled on the handler. Tracked under SOL-152091.
- On graceful shutdown, the metrics meter provider (SOL-152091) is now flushed and stopped through the shared shutdown-hook registry (SOL-152449). The Prometheus exporter is pull-based, so nothing is buffered to lose today — this is for a clean shutdown and to carry any future push-based exporter. Tracked under SOL-153884.
- An OpenTelemetry tracer provider with OTLP gRPC export is now wired at startup, gated by `OBS_TRACING_ENABLED` (off by default, door-closing policy): off, `New` does nothing, leaving the OTel API's own non-recording global default in place; on, it installs a real provider, so the span-instrumentation stories that follow (MCP entry, executor, SEMP-per-attempt, retry, token-exchange spans) call `otel.Tracer(name)` today with no wiring of their own. OTLP endpoint and TLS come from the standard `OTEL_EXPORTER_OTLP_ENDPOINT` / `OTEL_EXPORTER_OTLP_INSECURE` env vars with no code in this binary. Sampling honors `OTEL_TRACES_SAMPLER` / `OTEL_TRACES_SAMPLER_ARG` when both are set; with neither set, the SDK's own default applies (`parentbased_always_on` — sample everything, the v1 pilot intent), and `OTEL_TRACES_SAMPLER_ARG` alone, with no `OTEL_TRACES_SAMPLER`, is not read at all — set both together, per `docs/observability.md`. Two new self-observation instruments, `mcp_otel_spans_exported_total` and `mcp_otel_spans_dropped_total{reason}` (`export_timeout`, `export_error`, `shutdown`, and a reserved `queue_full` — see the known limitation below), register against the metrics meter provider (SOL-152091) whenever one exists; otherwise (metrics off, or its endpoint failed to start) a periodic `event=otel_self_stats` INFO log reports the same totals every `observability.otel_self_stats_interval_s` (default `60s`) instead, so an operator reading `kubectl logs` can diagnose OTLP export health without a working metrics endpoint. `export_timeout` is classified from the real OTLP gRPC exporter's own timeout shape (a gRPC `DeadlineExceeded` status), not only a bare `context.DeadlineExceeded`, so a stalled collector doesn't silently count as a generic `export_error` instead. Shutdown drains the exporter through the shared shutdown-hook registry (SOL-152449), bounded by its flush budget — `shutdown` counts one event per incomplete drain, not one per dropped span, since the SDK doesn't report how many spans it failed to flush. **Known limitation:** `queue_full` is defined in the reason enum for schema completeness but never increments in v1 — `go.opentelemetry.io/otel/sdk`'s batch span processor drops queue-overflow spans against an internal counter with no public accessor, so there is no supported way to observe that specific reason from outside the SDK; disclosed rather than faked. **Also not yet wired:** the OTel resource (`service.name`, `deployment.environment`, `cloud.region`, …) this provider is meant to share with the metrics meter provider — SOL-152091 doesn't construct one either, and those identity fields don't exist on `ObservabilityConfig` yet; both land together in the story that adds them (SOL-152425). Tracked under SOL-152420.
- A single OTel identity resource is now shared by the metrics meter provider (SOL-152091) and the tracer provider (SOL-152420), plus mirrored onto every log line from immediately after config loads onward (the process-banner and config-load-attempt lines before that have no identity to attach, since it derives from config) — closing the "not yet wired" gap disclosed in both of those entries above. New `internal/observability/resource` is the one construction site: `service.name` (new `observability.service_name` YAML field, default `solace-broker-mcp`), `service.version` (build-time injection, unchanged), `service.instance.id` (new `observability.service_instance_id` override, else the pod name via the new `POD_NAME` downward-API env var in `deploy/kubernetes/deployment.yaml`, else the process hostname), and, when configured, the new `observability.deployment_environment` and `observability.cloud_region` YAML fields. The last two are omitted entirely when unset, not defaulted to an empty string. On the metrics scrape surface these ride on `target_info`, unchanged in cardinality — no first-party metric gains a new per-series label; `metrics.New` now rejects a nil resource rather than silently emitting an unlabeled `target_info`. Log lines carry only the subset the FD commits to (`service.name` and, when configured, `deployment.environment.name` / `cloud.region`); `service.version` and `service.instance.id` do not leak onto logs. **`deployment.environment.name`, not the FD's original `deployment.environment`:** OTel renamed the semantic-convention key ahead of this story landing, and the SDK's own `resource.Default()` (merged into this resource) is already built against the renamed key, so keeping the older name would have shipped an attribute the SDK's own semantic-convention package no longer recognizes on day one — disclosed as a deliberate deviation from the FD text. **Known limitation:** `service_name` and `service_instance_id` always win over the standard `OTEL_SERVICE_NAME` / `OTEL_RESOURCE_ATTRIBUTES` environment variables, because config always has a value for both by the time the resource is built; `deployment_environment` and `cloud_region` don't have this problem, since config leaves them genuinely empty when unset. An operator wanting either standard env var honored should use the `observability.*` config fields instead, for now — see `docs/observability.md`. Tracked under SOL-152425.

- The OAuth token-exchange call now gets its own OpenTelemetry span, `tokenexchange.Exchange` (Story 50, SOL-153333) — the first application span this server creates (the tracer provider itself landed under SOL-152420). One span per call: a cache hit, a singleflight follower, and the singleflight winner triggering a live IdP round trip each get their own, created from the caller's own context so it nests under whichever span is active at the call site (a future SEMP-per-attempt span once Story 26 lands). `cache_hit` (bool) distinguishes a served-from-cache call from one needing a live round trip; `correlation_id` joins the span to the same request's logs and audit records; `outcome` follows the shared success/error/cancelled vocabulary (ADR-009), with a failed span's status set to `codes.Error` so trace backends that key error views off span status (not a custom attribute) surface it correctly. Cancellation is classified by **where** the error originated, not by Go error type alone: a caller's own context ending the call — `context.Canceled` **or** `context.DeadlineExceeded`, for example the SEMP retry budget in `internal/semp/resilience/sender.go` expiring while the exchange waits — is `cancelled`, while a `context.DeadlineExceeded` from the exchange's own internal retry-chain deadline is `error`; classifying every `DeadlineExceeded` as `error` regardless of source would have misattributed a caller's own timeout to the exchange. `error_type` is deliberately never set on this span: the existing closed `error_type` vocabulary (`internal/observability/audit`, computed in `internal/tools`) is scoped to tool-invocation outcomes and has no value describing a token-exchange failure mode; `docs/observability.md`'s span-attribute table now documents this as a stated exception. A follower's span carries `singleflight_role: "follower"`, a span `Link` to the winner's own span, and `winner_trace_id`/`winner_span_id` for backends that don't render a link's target inline; the winner's own span carries `singleflight_role: "winner"` and no link. Tracked under SOL-153333.
- Per-tool RED (Rate/Errors/Duration) metrics are now emitted on the `/metrics` endpoint (SOL-152091): `mcp_tool_invocation_total` (counter) and `mcp_tool_invocation_duration_seconds` (histogram, buckets `1ms, 5ms, 10ms, 50ms, 100ms, 500ms, 1s, 5s, 10s`), both labelled `tool`, `broker`, `outcome`, `error_type`, plus an unlabelled `mcp_http_active_requests` gauge that tracks in-flight requests for separating a capacity problem from a tail-latency one. They are observed at the single deferred per-invocation site every tool already logs through, so every tool the server exposes is covered with no per-tool instrumentation, and the gauge decrements from a `defer` so a panicking request cannot leak an in-flight count. `outcome` is one of `success`, `error`, `cancelled` (the `cancelled` value is reserved here and wired by a later story) and the failure cause rides a separate `error_type` label — a closed set of twelve values, empty on any non-error outcome — following the OTel semantic-convention pattern of pairing a small status enum with an `error.type` attribute; a recovered panic reads `outcome=error`, `error_type=panic`, never its own outcome value. The `broker` label is canonicalized to the configured aliases plus the sentinels `none`/`unknown`, so a caller cannot mint unbounded series with a mistyped broker; the log line keeps the raw alias for diagnostics. All label domains are finite, keeping cardinality bounded. The whole capability is gated by `OBS_METRICS_ENABLED` and emits nothing, gauge included, when off. Tracked under SOL-152086.

- The audit-record schema documented in `docs/observability.md` is now enforced in code, by a single constructor in the new `internal/observability/audit` package rather than by each emission site reproducing the rules. `audit.NewEvent` validates the field-applicability table per `audit_event_type` and refuses to build a record that breaks it — `error_type` only on an `operation` record and only when `outcome` is `error`; `reason` only on the three denial/failure record types, each against its own closed vocabulary so an authentication reason cannot land on an authorization record; `arguments_hash` never on a denial, because the call was refused before its arguments were dispatched. Identity is read from the request's canonical principal (SOL-152087), never supplied by the call site, so a record cannot name a caller other than the authenticated one, and only `principal.sub` and `agent_client_id` are written (Q-013). No record is emitted by this change; the constructor is what SOL-152096 and the stories after it emit through. **Three schema corrections land with it, all of them documentation catching up to the code:** the `audit_event_type` closed set is **seven**, adding `broker_authz_denied` for a broker-side (hop-2) authorization denial, whose emission site ships separately under SOL-153332 — a hop-2 denial produces that record *and* the call's `operation` record, so a SIEM query must match on `audit_event_type` rather than assume one record per call; the `error_type` closed set is **twelve**, not the ten `docs/observability.md` listed, because `bad_request` and `not_found` are emitted by the two tools that handle their own dispatch (`list-brokers`, `describe-semp-schema`) and by the argument-parsing guard ahead of every tool, none of which earlier counts of the main dispatch path included; and the field-applicability table gains its `broker_authz_denied` row. Nothing about the records the server emits changed — the lists were incomplete. A new AST-walking test (`internal/tools/audit_error_type_drift_test.go`) now derives the `error_type` set from the emit sites themselves and fails if it ever diverges from the vocabulary the constructor accepts, so the next addition breaks the build instead of the audit trail. Tracked under SOL-152090.
- Destructive tool calls now emit an audit record. With the new `OBS_AUDIT_LOG_ENABLED` flag on (off by default, door-closing policy), a destructive invocation writes one `event=audit`, `audit_event_type=operation` record at completion, carrying `principal.sub` and `agent_client_id` from the request's verified token, `tool`, `broker`, `arguments_hash`, `correlation_id`, `started_at_utc`, `duration_ms`, `outcome`, and `error_type` on a failure. One record per call, written when the outcome is known — no started/completed pair for a reviewer to join, and no doubled noise in a quarterly access review. A recovered panic still produces one, with `outcome=error`, `error_type=panic`, `panic_recovered=true`: a destructive handler that crashed may already have changed the broker, so a missing record must never read as "nothing was attempted". Read-only calls are not audited. **With the flag off, behaviour is unchanged** — the `executing destructive operation` WARN is emitted exactly as before, byte for byte, and no audit record is written; the capability is inert when off, not degraded. **"One record per call" bounds the `operation` record type, not the total**: a call the broker denies at hop 2 will also produce a `broker_authz_denied` record once SOL-153332 lands, and both are correct, so match on `audit_event_type` rather than counting records per correlation ID. **`arguments_hash` is computed over the arguments the handler actually receives, not the raw `tools/call` payload**: `broker` is excluded (so two calls differing only in the caller's casing of it hash identically, instead of the digest being salted by casing that never reaches the handler), and any key matching the same Never-Log pattern `docs/internal/secure-logging-rules.md` Rule 3 redacts on log output (`password`, `token`, `secret`, `authorization`, `credential`, `api_key`, `private_key`) is replaced with a fixed placeholder before hashing, recursively — closing a gap where a free-form composite argument (e.g. `update-message-vpn`'s `msgVpnConfig`) could otherwise carry a broker password into the digest's pre-image, which the `arguments_hash` attribute key itself does not match against that same redaction net. `docs/observability.md`'s hash-reproduction recipe documents both transforms. Tracked under SOL-152096.
- Audit records that cannot be written are now reported rather than lost. A failed write produces an `audit_drop` record that keeps `event=audit`, so the one record saying audit records are missing stays inside the filter a customer routes the audit stream on. Three things produce one: the log handler refusing the write, arguments that could not be canonicalized for hashing, and — the case most likely to reach an operator — the record's level being filtered out. An `operation` record is `INFO`, so enabling the audit log on a server running at `warn` or `error` would otherwise erase the audit trail silently; the drop record is emitted at `ERROR`, the highest level `log_level` accepts, so it survives **every** supported log level — including the one that suppressed the record it reports. A drop at `WARN` would itself have been filtered out at `log_level: error`, reintroducing exactly the silence it exists to prevent. **The drop record now carries optional attribution** — `dropped_audit_event_type` (which record type could not be built or written), `tool`, and `broker` — set on both drop sites in `internal/tools` (a hash failure, a constructor rejection), so a reviewer working inside the audit stream can attribute a gap without joining to the operational log line, which is exactly the join a level-filtered *successful* call cannot make (its own `tool invoked` line is `INFO`, filtered at the same levels the drop survives). All three fields are optional and absent when a call site does not know them; `audit_schema_version` moves to `1.1` for this additive change. The `mcp_audit_events_dropped_total` counter that makes drops dashboard-visible is not registered yet and is tracked separately; the record ships now, with no dependency. Tracked under SOL-152096.
- `audit.HashArgs` computes the `arguments_hash` an auditor reproduces: a lowercase hex SHA-256 over the RFC 8785 (JSON Canonicalization Scheme) form of a tool call's arguments, via the new `github.com/gowebpki/jcs` dependency (Apache-2.0). A published canonicalisation spec rather than a hand-rolled one is the whole point — number serialisation, Unicode handling, and recursive key ordering are where a home-grown canonicaliser diverges silently, producing a digest a customer's own Python, Java, or Rust tooling cannot reproduce and our tests would not catch. Raw argument values never enter an audit record; the digest is the only representation of them the schema carries. Hash stability is pinned by goldens whose expected digests were computed outside Go from hand-derived canonical forms, so a change in canonicalisation output fails CI loudly rather than silently orphaning every hash emitted by an earlier build. `docs/observability.md` now carries the RFC reference, a reproduction recipe, and the additive-only schema commitment. Tracked under SOL-152090.
- Two new log signals make it visible when the server is pacing or shedding requests to protect a broker, rather than something else being slow. Both are gated on `OBS_SATURATION_EVENTS_ENABLED` (default off, following the door-closing policy) and both reuse the `stage` vocabulary (`rate_limit`, `concurrency`) introduced by SOL-153442, so they never disagree with the shed warning about which gate is involved. `broker admission slow: request still waiting to be admitted` fires at `WARN` once per request whose admission wait passes `observability.saturation_threshold_ms`, carrying `stage`, `waited`, `threshold` and `max_queue_wait`. It fires **while the request is still waiting**, not when the wait resolves: a resolution-time line would arrive up to `max_queue_wait` later, and under the supported `max_queue_wait: 0` setting it would never arrive at all, which is exactly the unbounded case that most needs a signal. It does not re-fire on a timer — one line per request, whatever the outcome — and a request that goes on to be shed is still reported separately by the existing shed warning. `broker in-flight occupancy` fires every `observability.otel_self_stats_interval_s` (default `60s`) for each broker carrying load, carrying the broker alias, `in_flight` and the configured `limit`, at `WARN` when the two are equal and `INFO` below; idle brokers are skipped so the presence of a line is itself the signal, and brokers the server has never connected to do not appear, since broker clients are created on first use. **This is an interim signal, not the metric the observability roadmap described.** `docs/observability.md` listed `mcp_saturation_total` and a rate-limiter health gauge on the Prometheus `/metrics` endpoint SOL-152091 added above; that endpoint exists, but nothing registers a meter provider or these instruments on it yet, and standing that up here would duplicate work already in flight under SOL-150254, so the metric form stays on the roadmap and that document now marks this capability `[Interim — logs only]` rather than shipped. Neither log line is a stable interface; the compatibility commitment will live on the metric that replaces them. Tracked under SOL-153443.

- A recovered panic is now visible from outside the process. New `mcp_panic_recovered_total{boundary}` counter, registered against the existing meter provider (SOL-152091) and exposed on `/metrics`, increments at both of the server's request-path recovery nets: `boundary="http"` for the middleware wrapping the whole mux (SOL-151286) and `boundary="tool"` for the MCP tool-dispatch wrapper (SOL-151287). Both stories were scoped with this counter in their acceptance criteria and shipped without it, so until now the only trace of a recovered panic was an ERROR log line an operator had to know to grep for — nothing to alert on. One counter with a `boundary` label rather than two metric names, so a single alert covers both nets; neither label value can be named from outside the owning package, which exposes one recording function per boundary and no way to pass an arbitrary one, so the two-series cardinality bound is a property of the API rather than a convention. **Both series are published at zero from startup.** A counter that appeared only on its first increment would have defeated the alert this ticket exists to enable: PromQL's `increase()` needs two samples in the window, so the sample that creates a series is only a baseline and a process's first panic would have passed unnoticed. Seeding also makes a flat zero read as "nothing panicked" rather than "No data", and makes `absent()` a usable "the counter was never wired" alert. The tool-path panic log also now carries `event="panic_recovered"`, the attribute the HTTP middleware and the three non-request-path panic nets (`internal/safego`, token exchange, OTLP self-stats) already emitted, so an alert keyed on that attribute no longer silently misses tool panics. `http.ErrAbortHandler` stays exempt from both the log and the counter on the HTTP boundary: `net/http` uses it as a client-disconnect sentinel and the MCP streamable/SSE path raises it on ordinary teardown, so counting it would fire a panic alert on routine traffic. **The counter covers only panics on a request's own goroutine.** A panic on a goroutine a handler spawns is recovered by `internal/safego` (the SEMP fan-outs in the broker-status, queue-metrics and discard-stats handlers, and the composite executor) or by `internal/tokenexchange` and converted to an error that returns normally, so the tool-dispatch net never sees it and `boundary="tool"` does not move. Those sites still log `event="panic_recovered"`, so an alert on the log attribute has wider reach than one on the metric; `docs/observability.md` states the gap and its call sites rather than leaving an operator to discover it from a flat graph. Recovery itself is unchanged and remains unconditional — with `OBS_METRICS_ENABLED` off, no instrument is registered and the increments are no-ops. **No change to what either caller receives:** a tool-path panic still returns `isError: true` with a generic message and `retryable: false` over a successful MCP call, per the spec's application-error convention, and an HTTP-boundary panic still returns a clean `500`; both are now pinned by tests that assert the response shape rather than discarding it. Tracked under SOL-154037.

### Fixed

- In stateful streamable HTTP sessions (go-sdk v1.7.0), the bearer token and correlation ID carried on tool-handler contexts were frozen at `initialize` time and replayed on every subsequent `tools/call` in the same session. This is a structural property of the SDK's session model — the streamable handler keeps one handler context per session and does not replace it per POST — not a mix-up between sessions or users. The practical effect was that Hop 2 exchanged the `initialize` request's bearer regardless of which token the agent sent on the current POST, and correlation IDs on SEMP calls (and in `CallToolResult.Meta`) identified the `initialize` request including any server-generated ID that request carried, rather than the current one. The fix decouples per-request state from the frozen session context: `auth.RequestExtraMiddleware` (always registered) copies `Extra.Header` — populated by the SDK's streamable transport from the raw HTTP request headers on each POST — onto the handler ctx using `WithRawSubjectToken` and `correlation.With`, so the values Hop 2 and the correlation stamp read are always this POST's. Hop 2 now exchanges this request's bearer only when the SDK has already validated it (`Extra.TokenInfo != nil`, mirroring `auth.PrincipalMiddleware`'s own gate); correlation IDs on tool calls and SEMP requests follow this POST, including IDs the server generated when the client omitted the `X-Correlation-ID` header (commit 2 of the fix stamps the resolved ID onto the inbound header so `Extra.Header` carries it) — and only when `OBS_CORRELATION_ID_ENABLED` is on, matching the HTTP correlation middleware's own gate, so a client-supplied `X-Correlation-ID`/`traceparent` cannot revive correlation IDs while the capability is off. Tracked under SOL-153935.

- Token-exchange log lines that previously carried no `correlation_id` now carry the ID of the request that triggered them: the lines under the detached exchange context (the broker-token IdP request/response lines, the cache-put outcomes including the `token cache put failed` WARN, and `broker token request retries exhausted`), the recovered-panic ERROR, the Retry-After gate WARNs, and the audience-mismatch WARN. Previously a cache put could not be joined to its get without timestamp guessing. When several concurrent requests share one exchange, these lines carry the initiating (singleflight winner's) request ID; each caller's own `broker token exchange completed` line is unchanged and still carries its own. The circuit-breaker state-change WARN stays without an ID on purpose (a transition is the verdict on a window of failures, and attributing it to one request would mislead), as does the startup config-load WARN (no request exists yet). With correlation disabled, output is unchanged. Tracked under SOL-153364.
- The configuration files this project ships for operators to copy — `broker-config.example.yaml` and the ConfigMap in `deploy/kubernetes/` — no longer default to a mode that cannot start without an identity provider. Both previously set `mcp_client_auth.mode: oauth` while omitting the `tool_authorization` block that mode makes mandatory, so both failed at config load: `kubectl apply -f deploy/kubernetes/` produced a crash-looping pod, and a user copying the documented example hit the same error. Supplying the missing block alone was not enough — the server then tried to reach the placeholder `issuer: "https://idp.example.com"` and exited. The example now defaults to `mode: disabled` and the ConfigMap to `mode: static` with a `DEV_TOKEN` read from the Secret, since a pod must bind all interfaces and `mode: disabled` on a routable bind would require acknowledging unauthenticated access. Production OAuth is carried in both files as commented-out sample lines to uncomment, co-located with the other modes at the point where the mode is chosen, and naming the two settings that are easy to miss (`tool_authorization.enabled`, `tls_terminated_upstream`). `DEV_TOKEN` ships empty rather than with a default value: the Kubernetes manifests deliberately fail closed with `mcp_client_auth.dev_token is required`, because a working default would mean an unedited apply brings up a cluster-routable MCP server whose only credential is a string published in this repository. Note that the dev modes bind `127.0.0.1`, which inside a container is the container's own loopback — `README.md` and the example now spell out the bind/token combination a container needs, since the previous oauth default happened to bind all interfaces. A new `deploy/kubernetes/README.md` documents which placeholders must be edited before applying and records that GHCR image tags carry no `v` prefix (`0.8.0`, not `v0.8.0`, which fails with `manifest unknown`). A new `internal/config/shipped_examples_test.go` loads the active configuration of both shipped files through the server's own validator, asserts neither ships in production mode, that the standalone example never lifts its loopback-only bind, and that the Kubernetes config ships a shared token, so the schema drift that caused this, a future re-introduction of an unreachable-issuer default, and an unauthenticated default on a routable bind all fail in CI instead of in an operator's cluster; the commented-out sample blocks remain unverified by it. Tracked under SOL-153712.
- Idle MCP sessions are now closed after two hours instead of being held for the lifetime of the process. The server passed no options to the SDK's streamable-HTTP handler, leaving `SessionTimeout` at its zero value — which the go-sdk documents as "idle sessions are never closed". A session was released only on an explicit `DELETE` or a transport close, so any client that connected and then vanished (a sleeping laptop, a killed container, a dropped network, or a client that simply never sends `DELETE`) left its session and the goroutines behind it in memory permanently. On a long-running server this grew without bound and no metric revealed it. Operator-visible effect: a client whose session has been idle for more than two hours receives `404 session not found` on its next request and re-initializes; spec-compliant clients do this transparently. Tracked under SOL-153582.
- A request to a saturated broker now fails within a bounded time instead of waiting forever. `Sender.Do` gates every request on two per-broker queues in sequence — the pacing interval (`semp.request_min_interval`) and the in-flight cap (`semp.max_concurrent_per_broker`) — and both blocked on the caller's context alone. Nothing upstream supplies one: `cmd/server/main.go` leaves `http.Server.WriteTimeout` at zero to keep MCP streamable connections alive, so a caller that sets no deadline of its own had none at all, and sustained saturation was an indefinite hang with no signal that anything was wrong. This was carried as an accepted risk in `docs/internal/threat-model.md` ("Unbounded goroutine/queue buildup..."), now closed. A new `semp.max_queue_wait` (default `30s`) bounds both gates as a single budget measured from entry to `Do`, not one budget per gate, so the caller-visible ceiling is the configured value rather than double it. Covering the semaphore is the substance of the fix, not an extension of it: the rate limiter drains at a fixed pace and only backs up while arrival rate exceeds it, whereas a semaphore slot is held for a request's entire retry chain — roughly 16 minutes at default settings — so a degraded broker fills every slot and bounding the limiter alone would have moved the hang one line down rather than removing it. A request that cannot be admitted in time is rejected before it is sent, with a new `resilience.BrokerBusyError` that surfaces to the agent as `retryable: true` plus a `retryAfterMs` hint and an `error_source` of `load_shed`; because nothing reached the broker, this is the one retryable failure with no idempotency caveat, safe to repeat even for a write. `retryAfterMs` reports the configured bound rather than the pacing interval, so shed callers do not all return at once and re-form the queue. Each rejection logs at `WARN` as `request shed: broker admission bound exceeded` with a `stage` field of `rate_limit` or `concurrency`, naming which gate ran out of budget. A caller that does set its own deadline is unaffected and still receives `context.DeadlineExceeded`, never a busy error. Operator-visible effect: under sustained saturation, calls that previously hung now return an error after roughly 30 seconds. The default is sized to break hangs rather than to shed load, though the two gates give it different amounts of room: at the default pacing interval it absorbs a backlog around 300 requests deep, so ordinary queueing at that gate is unchanged, but the in-flight gate is tighter than it looks — a slot is held for a whole retry chain and `request_timeout_duration` alone defaults to `1m`, so a healthy but slow broker holding every slot for 30 seconds or more will shed the next caller with nothing actually wrong. `docs/configuration.md` documents how to size the bound against whichever gate a deployment hits. Deployments that want a faster signal can lower it, and `max_queue_wait: 0` restores the previous unbounded behavior. Tracked under SOL-153442.
- A `tools/call` request with a missing or malformed `arguments` field now reaches the audit log and comes back as a structured tool result (`isError: true`, `retryable: false`), instead of bypassing the audit log entirely and returning a bare JSON-RPC protocol error. The tool-dispatch closure in `register.go` unmarshaled `req.Params.Arguments` before `ToolManager.CallTool` ever ran; since `Arguments` carries `omitempty` on the wire, a client sending `tools/call` with no `arguments` field at all — or a genuinely malformed, non-object payload — failed `json.Unmarshal` and returned straight from the closure, before `CallTool`'s own audit `defer` could fire, so every such request was invisible to the audit surface. An omitted `arguments` field is now treated the same as an empty object and flows into normal validation (a tool with other required parameters still fails there, e.g. a missing `broker`, fully audited); a genuinely malformed payload is now audited by the dispatch closure itself and answered with the manager's normal structured error shape, with a static client-facing message rather than the raw decode error. Tracked under SOL-153765.

### Changed
- Updated the embedded SEMPv2 OpenAPI specs to the 10.26.5 rolling release (`10.26.5.11206`), so tool schemas track current broker attributes. The three spec files are renamed to `semp-v2-swagger-{action,config,monitor}.10.26.5.json` and continue to be sourced from the private-extended variant.

- Each broker's request pace is now shared fairly across callers instead of being served first-come-first-served, so one caller's burst can no longer starve every other caller of the same broker. Both admission gates in `Sender.Do` were plain Go channel operations, and Go's channel wait queues are FIFO, which put every later caller behind the whole of an earlier caller's backlog. It took no misbehaving client to hit: one `list-*` call over a large message VPN fans out one SEMP request per row, so a single tool invocation can enqueue hundreds of requests, and at the default `100ms` pace a 500-deep backlog is 50 seconds of queueing for someone else's status check. A new per-broker admission scheduler now allocates the pace round-robin over **two** rotation levels: the outer level is the OIDC subject, the inner level is that subject's MCP sessions. Both levels are needed, in opposite directions. Keying on the subject alone would collapse an entire agent platform into one bucket under an OAuth `client_credentials` grant, where the subject is a shared service account. Keying on the `(subject, session)` pair as one flat identity would do the reverse and let a caller multiply its share by opening sessions, which are freely mintable — a subject with ten sessions would take 91% of the pace from a single-session caller. With the outer rotation over subjects, a subject gets one turn per lap however many sessions it holds, and its sessions take turns within it. In-flight slots are gated separately and nested the same way: each subject may hold up to `max(1, ceil(max_concurrent_per_broker / active subjects))`, and within that allowance each of its sessions up to `max(1, ceil(subject allowance / that subject's sessions))`. Both levels are load-bearing — without the subject level a caller multiplies its concurrency by opening sessions, and without the session level one session takes its subject's whole allowance and starves its siblings, which under `client_credentials` means no protection at all since there is only one subject. The last free slot is withheld from a caller that already holds one whenever a peer is queued and holds none, so an arriving caller waits for a single completion rather than for a whole retry chain; when no such peer exists the slot is granted normally, so the rule costs no capacity. Measured against a stub broker with one caller at 20-way concurrency and one caller issuing a single request at a time, both figures from committed tests: the steady caller gets about 6% of the broker's pace with `fair_scheduling` off and about 50% with it on. Aggregate ceilings are unchanged — `semp.request_min_interval` and `semp.max_concurrent_per_broker` still hold across all callers combined, a single active caller still receives the entire configured rate and the entire in-flight cap, and this closes the `docs/internal/threat-model.md` row "One client starves every other legitimate caller of the same broker". Six limits are deliberate and documented there and in `docs/configuration.md`: fairness is per pod rather than per cluster (the shipped manifests run two replicas), a newly arrived caller waits for a completion rather than being handed a reserved slot (nothing is reserved for a caller that has not arrived), a single session's own fan-out still queues behind itself, callers multiplexed by a client over one session and one token share a bucket, `request_min_interval: 0` removes pace fairness entirely because there is no pace to share, and queue depth remains bounded in time by `semp.max_queue_wait` rather than in depth. Per-caller state is created on enqueue and deleted once a caller has nothing queued and nothing in flight, so nothing accumulates over the life of the process and there is no TTL or sweeper. A new `semp.fair_scheduling` (default `true`) turns it off, restoring the previous first-come-first-served admission byte for byte; it is a kill switch for blast radius, not a capacity control, since it adds no throughput. Its effective value is reported on the `config loaded` startup line so a pod's mode is auditable. A request still queued when a broker client is closed is now reported as the same retryable "broker busy" error a shed request gets, rather than an opaque internal error, because it was never sent and a rolling restart is routine. The saturation and shed warnings (`broker admission slow`, `request shed`) now also carry a `caller_sub` field, the same sanitized, 256-byte-capped subject projection the audit log uses, so an operator triaging a fairness incident can see which caller is being throttled without either log line re-exposing the untruncated claim. Operator-visible effect: under contention the latency distribution shifts, by design — a caller with a deep backlog sees its own requests take longer so that other callers' do not. Tracked under SOL-153441.

- `observability.saturation_threshold_ms` now defaults to `1000` rather than `10`, and is defined as the time a request spends queued for admission to a broker rather than end-to-end tool-call latency. Nothing consumed the setting before now, so no existing behavior changes; the old value predated a consumer and, against the default `semp.request_min_interval` of `100ms`, would have reported effectively every request as saturated. The default sits ten pacing intervals above the default pace and well inside the `30s` `max_queue_wait`, so the warning arrives long before a request is shed. Deployments that lower `request_min_interval` or run high concurrency should raise the threshold rather than read the resulting volume as saturation. Tracked under SOL-153443.
- The DEBUG logs for acquiring a broker token now trace the whole sequence, from `broker token needed` through to `broker token attached to request` or `broker token unavailable`. The old messages are replaced: `token cache get`, `token cache put` (both carried a `status` field of `0` or `1`), `token exchange succeeded`, `token exchange retried` and `token exchange retries exhausted` are gone. New fields on these lines: `http_status`, `attempts`, `reason`. Anything matching the old messages or reading `status` on the cache lines needs updating. Tracked under SOL-153363.
- The per-invocation tool log line (`msg="tool invoked"`) now carries `outcome` instead of `status`, with the same `success`/`error` values, so the log field shares one key with the new `outcome` metric label and the audit/trace vocabulary. Anything grepping or dashboarding on `status` for these lines needs updating. Tracked under SOL-152086.
- The IdP token endpoint on a failed token-exchange log line is now reported under `idp_endpoint` instead of `token_endpoint`, and any userinfo in the URL is stripped before logging. The old key contained the substring `token`, which the server's log-redaction safety net matches on, so the value reached operators as `[REDACTED]` on every token-exchange failure, hiding the one field that distinguishes a misconfigured IdP endpoint from an unreachable one. Transport failures still showed the URL incidentally, inside the `detail` field's underlying `*url.Error` text; the rejected, invalid-response, circuit-open and rate-limited classes lost it outright. Anything grepping or dashboarding on `token_endpoint` needs updating. Tracked under SOL-153827.
- Duration fields on the token-exchange log lines are now strings (`"77.496667ms"`) rather than raw nanoseconds: `exchange_total_elapsed` (renamed from `exchange_elapsed`), `waited`, `retry_after`, `requested` and `clamped_to`. Anything consuming one as a number will break. Durations elsewhere, including `duration` on `tool invoked`, are unchanged. Tracked under SOL-153363.
- The composite tool executor now compiles each step's `args`/`forEachIf` Go templates once, at `LoadTools` startup, instead of re-parsing them on every step call. A fan-out step like `list-vpns`' `real-clients` probe triggers 4 template parses per row, so a single call against a broker with hundreds of VPNs re-parsed roughly 2,000 templates that are static for the life of the process. Internal Go API only; the on-the-wire MCP schemas, tool behavior, and response bytes are unchanged. One incidental effect: a syntactically invalid `args`/`forEachIf` template in `tools.yaml` now fails at server startup instead of only on the first invocation that reaches it — not reachable with the embedded, tested `tools.yaml` this project ships. Tracked under SOL-153764.
- The example Kubernetes manifests in `deploy/kubernetes/` now default to two replicas, so a rolling update or node drain no longer takes the service fully dark. Two distinct mechanisms deliver that and each covers only its own case: `deployment.yaml` pins `strategy.rollingUpdate.maxUnavailable: 0` / `maxSurge: 1` for rollouts (a Deployment rollout deletes pods directly and never consults a PodDisruptionBudget — inherited defaults happened to compute the right numbers at exactly two replicas, which was too incidental to rely on), while the new `poddisruptionbudget.yaml` covers drains and cluster upgrades via the Eviction API. That PDB uses `maxUnavailable: 1` rather than `minAvailable: 1`: the two are equivalent at two replicas, but `minAvailable: 1` against `replicas: 1` permits zero disruptions and hangs every drain of that node indefinitely, so the safer spelling avoids a footgun for anyone who scales a copy back down. `deployment.yaml` also adds best-effort `topologySpreadConstraints` across nodes, because two replicas in one failure domain leave node failure — which is involuntary, and bypasses the PDB — a full outage. Because the MCP streamable-HTTP handler is stateful — it issues an `Mcp-Session-Id` and holds the session in process memory, per pod — `service.yaml` also sets `sessionAffinity: ClientIP` to pin a client to the pod holding its session; without it a client's follow-up requests round-robin onto a pod that answers `404 session not found`. **That affinity is enforced by kube-proxy on the ClusterIP path only, and an Ingress, Gateway, or service mesh in front of the Service bypasses it entirely** — including the TLS-terminating-ingress topology `docs/authentication.md` recommends for OAuth; behind any of those, stickiness must be configured at that layer, and *not* on the `Mcp-Session-Id` header, which cannot work (see the SOL-153834 entry above and `deploy/kubernetes/ingress.yaml.example`), or the deployment stays at one replica. Its 3h window must also stay above the 2h session idle timeout. Operator-visible effect of running two replicas: sessions do not survive pod replacement, so a rolling update ends every in-flight session and those clients receive `404 session not found` on their next request and re-initialize — transparently for spec-compliant clients, as with the idle-timeout case above. Container resources changed in the same pass: `limits.cpu` is removed (a CPU limit throttles via CFS at burst, which is this workload's normal shape, while `requests.cpu` guarantees this pod's share under contention) and memory moves to `requests: 128Mi` / `limits: 512Mi`. Note a namespace `ResourceQuota` requiring `limits.cpu` will reject a pod that omits one, and a `LimitRange` defaulting it will silently reinstate the throttling. These are copy-and-edit examples, not a supported product surface. Tracked under SOL-152089.
- The caller identity on the `tool invoked` audit line and on the `tool authorization` and `tool list filter` records is now read from a single canonical principal, built once per request from the verified token, instead of each log site re-reading the SDK's token info for itself. Emitted output is unchanged: the same four fields (`sub`, `iss`, `client_id`, `jti`), the same `<absent>` and `<verifier-bug>` sentinels, and the same byte shape, now pinned by a golden test of the `tool invoked` line in both auth-enabled and disabled modes, and by a test that the identity on a record tracks the token presented on that request rather than the one that opened the MCP session. The new `auth.Principal` carries the committed claim set `sub`, `scope`, `client_id`, `iss`, `jti`, deliberately excludes `preferred_username` and `email`, and is the identity the audit-event and metrics work that follows will name the acting principal by, so those records and this log line cannot drift apart. Sanitization of identity claims (control-character and bidi stripping, the 256-byte cap) now happens in one place, when the principal is built, and the `<absent>` normalization moved into the shared `sanitize` package. Population is MCP receiving middleware rather than HTTP middleware, which matters for correctness rather than taste: in stateful streamable HTTP the context a tool handler receives descends from the POST that established the session, not the current one, so an HTTP-middleware principal would have named the token that opened the session for the session's whole life — through every client token refresh. Registration order in `cmd/server` is load-bearing for the same reason and is covered by a test. Two small operator-visible improvements: the `ERROR` reporting a non-string claim now carries a `correlation_id` where it previously carried none, matching the one on the audit line that shows `<verifier-bug>` so the two can be joined — that ID was stuck at whatever `initialize` had rather than naming the request actually being handled, a pre-existing byproduct of stateful streamable HTTP building the handler ctx once at session establishment (not a real session-level identifier), which this entry does not change but the SOL-153935 fix above does, so in this release it narrows the search to the one request; and `docs/configuration.md` now documents both reserved sentinels and what an operator should do about each. Otherwise internal Go API only — `tools.NewIdentityFromTokenInfo` is replaced by `tools.NewIdentityFromPrincipal(auth.PrincipalFrom(ctx))`; on-the-wire MCP schemas and operator config are unchanged, and no new log line is added. Tracked under SOL-152087.

### Security

- `SEMPError.Error()` no longer falls back to the raw, unparsed HTTP response body when a SEMP call's error response doesn't match the broker's own `meta.error` envelope — the case a reverse proxy, API gateway, or WAF hits when it intercepts the request and returns its own (non-JSON) error page instead of the broker's. That raw body is not broker-authored and has never been reviewed by this codebase, yet the tool-invocation audit log's `detail` field logged it verbatim, under a comment claiming the four "audited" broker error types (SEMPv1, SEMPv2, retry-exhaustion, token-exchange) carry only reviewed, broker-generated text — true for the other three and for SEMPv2's own `meta.error.description` field, but not for this one fallback. `Error()` now reports just the operation and HTTP status (`"<operation> returned HTTP <status>"`) when `Description` is empty; the `Description` branch itself is unchanged and continues to log and surface to the agent as before. The raw body remains available on the `Body` struct field for debugging but is deliberately rendered by no sink, matching the SEMPv1 client's existing equivalent. No config or tool-facing behavior changes; the only operator-visible effect is that `detail` on this one log path no longer echoes an intermediary's raw response text — the log line's `operation` and `http_status` fields still identify the failing call. Tracked under SOL-153766.

- The breaker's state-change WARN now carries a `consecutive_failures` attribute, so an operator can tell which rule (consecutive versus rate) opened the breaker from the log line alone. Tracked under SOL-152286.
- OAuth Protected Resource Metadata (PRM) is now also served at the RFC 9728 §3.1 canonical path `/.well-known/oauth-protected-resource/mcp`, in addition to the existing bare `/.well-known/oauth-protected-resource`. Both paths return the same document. The `WWW-Authenticate` challenge on a 401 continues to advertise the bare URL, so clients that follow the challenge verbatim (for example, Claude Code) are unaffected; clients that build the RFC 9728 canonical path directly (for example, the Automatic OAuth discovery feature in Solace Agent Mesh) now get a 200 instead of a 404. Tracked under SOL-153089.
- `CallTool` now returns a structured MCP tool result (`isError: true`, with a `retryable` field) instead of a bare JSON-RPC protocol error for every local failure path: a missing or unknown `broker` parameter, a parameter-schema validation failure, a handler returning a nil or invalid result, an output-schema validation failure, or a result that fails to marshal. Only the handler-execution-failure path did this before; every other branch returned a bare Go error, which the MCP spec's own guidance says should be a result the caller can see and self-correct on, not a protocol-level error. The three branches that matter most fire *after* the tool handler has already run — for a destructive tool (a delete, a disable, a purge), the broker-side action may have already succeeded by the time a nil/invalid result or a marshal failure is caught, and the caller previously had no `retryable` signal telling it the action already took effect versus never having run at all. Errors this package constructs itself (missing/unknown broker, validation, nil/invalid output) are shown to the caller verbatim, because they were already safe and specific; a broker-construction failure deep inside a client (for example, cookie-jar or authenticator setup) still goes through the existing suppression path that hides unvouched-for error text behind a generic message. An unrecognized tool name is unaffected — it stays a protocol-level error, matching how the MCP spec treats that case and how the SDK already rejects it before a call reaches this code in production. Tracked under SOL-152980.

### Security

- Cross-origin protection on the `/mcp` endpoint now runs *outside* the auth middleware instead of inside it, and logs its rejections. Previously the `net/http.CrossOriginProtection` wrap (added in `0.7.0` alongside the `go-sdk` v1.6.1 bump) sat between auth and the SDK handler, which had two consequences whenever `mcp_client_auth` was enabled: a browser-initiated cross-origin POST or DELETE was answered with a `401` from auth rather than the `403` it earned, masking a CSRF-shaped probe as an ordinary auth failure; and every such request paid full JWT and JWKS validation before being rejected. The wrap now sits in `buildMCPEndpoint` between correlation and auth, so the layer order is `limitRequestBody → correlation → crossOrigin → auth → mcp`. A rejection now returns `403` before any token work, logs at WARN with the offending `Origin` and `Sec-Fetch-Site`, and carries a correlation ID when `OBS_CORRELATION_ID_ENABLED` is on — matching the ADR-001 reasoning that already puts correlation outside auth so a `401` gets an ID. What passes and what is rejected on the wire is otherwise unchanged: safe methods (GET/HEAD/OPTIONS) always pass, so the SSE stream is never rejected on origin grounds, and requests carrying neither `Origin` nor `Sec-Fetch-Site` still pass as non-browser traffic. No new configuration; protection remains on by default. `docs/internal/threat-model.md` §1 gains the corresponding CSRF row, including the one client whose `Origin` behaviour is still unobserved. Tracked under SOL-152971.
- Broker URLs logged at four runtime sites — the once-per-alias "broker connection created" line, the `Sender`'s retry/failure logging (`internal/semp/resilience`), and both SEMPv1 and SEMPv2 `HTTPClient.LogValue` implementations — now go through the same `SanitizeURLString` sanitizer `BrokerConfig.LogValue` already applied, instead of logging the URL raw. `validateBrokerURL` already rejects any broker URL with embedded userinfo at config load in every mode, so none of these could carry a credential today; this closes the gap where that validation guarantee was the *only* thing standing between a broker URL and the log stream, with no independent defense at the log sites themselves and no coverage from the `ReplaceAttr` redaction safety net (its redacted-key list doesn't include `url`/`base_url`/`broker`). No behavior change for a valid, non-credentialed URL. Found in a Claude-assisted security sweep. Tracked under SOL-152979.
- Token exchange now logs a diagnostic `WARN` when the IdP-issued access token's `aud` claim doesn't include the audience this process actually requested for a broker. This is not a security control — the broker is the resource server and its own resource-server audience validation (on by default) is the real enforcement point, and this change doesn't touch that or the outcome of any exchange. The gap it closes: the broker validates the token against *its own* configured required-audience, but never sees what this process asked the IdP for, so if an IdP canonicalizes or ignores the requested audience (for example, the `api://` resource-URI prefixing Entra applies) and happens to issue a value the broker still accepts, nothing previously surfaced that the per-broker audience config was inert. The new check decodes the token's claims (without verifying its signature — the token already arrived over TLS from the configured, trusted IdP; this is a plaintext sanity check on an already-trusted response, not authentication) and logs the broker, the requested audience, and the token's actual `aud` value(s) bounded to 5 values of 200 characters each; it silently skips when no audience was requested (optional in V1) or the access token isn't JWT-shaped (RFC 8693 permits opaque tokens, and the broker's own audience validation has the identical blind spot when its access-token-parsing option is off). Deliberately **never fails the exchange**: different IdP families (Entra, Okta, Keycloak, Auth0) can canonicalize a requested audience into a different representation in the issued token, and a strict equality check would risk breaking a legitimately-configured IdP integration this project hasn't been tested against — trading a diagnostic gap for an availability regression, which is worse. Separately, the token-exchange dedup/cache key now includes the requested audience alongside subject token and broker alias: the key already included broker alias despite it never reaching the IdP request, while audience does reach the request and wasn't in the key — correct only because broker alias happens to determine audience 1:1 today, not because the key was self-sufficient. Found in an automated robustness/security sweep. Tracked under SOL-152981.

- The container health check (`--health`, the Dockerfile `HEALTHCHECK` command) now verifies the server's TLS certificate instead of accepting any certificate: it pins the certificate at `tls_cert_file` and verifies against the SAN that certificate carries. Closes CWE-295 / CodeQL `go/disabled-certificate-check`. Tracked under SOL-153167.

  **Upgrading a TLS-enabled container:** the probe now reports unhealthy — while the server keeps serving TLS correctly — if that certificate is unreadable from the probe's process, carries no DNS or IP SAN, has expired, or is not the one the server is presenting. Failure reasons now go to stderr, which Docker records in `State.Health.Log`. See [Configuration](docs/configuration.md) and the health check section of the [User Guide](docs/user-guide.md).

- New optional `mcp_client_auth.tool_authorization.filter_tools_list` flag narrows the `tools/list` response to the tools the caller's groups actually grant, instead of returning every registered tool to every caller. **Defaults to `false`** — absent behaves exactly as today, and with the flag off no middleware is installed, so the request path is unchanged. This is discovery hygiene, not an access control: `tools/call` remains the only authorization boundary and is enforced identically either way, and a tool absent from the list is still callable by name, because the server resolves tool calls against the full registered set rather than against whatever a previous list returned. The benefit is context — an agent handed tools it will be denied spends context on their descriptions and schemas and tends to misreport the cause when a call is refused; a caller in a narrow role can drop from ~24 tools to two or three. The filter reuses the same policy decision as the call path, so a listed tool is always callable and a callable tool is always listed; the two structurally exempt tools (`list-brokers` and `describe-semp-schema`) are never filtered, because hiding a tool that stays callable would break that guarantee and would remove broker discovery for every caller. A caller whose groups match no grants receives a normal response containing only the exempt tools — never an error, never an empty list — and a token carrying no groups claim at all fails closed to the same response. Those two cases are deliberately indistinguishable to the caller but are separated in the server log: each filtered list emits one `msg: "tool list filter"` line tagged `event: "tool_list_filter"`, carrying the usual caller identity fields plus `decision_reason` (`filtered`, `unfiltered`, `not_permitted`, or `missing_claim`), `groups_present`, and `tools_before`/`tools_after` counts. `missing_claim` logs at `WARN` because the token could not answer the authorization question at all — typically an IdP claim-mapper misconfiguration affecting every caller of that deployment — while every other outcome logs at `INFO` as the policy working as configured; caller group names are never logged, matching the call path. Setting the flag while `tool_authorization.enabled` is `false` logs a startup `WARN` naming the reason and leaves filtering off rather than failing startup: there is no policy to filter against, so the state is inert rather than incorrect, and it is what an operator produces by flipping the master switch without touching anything else. The filtering posture is stated on every boot alongside the existing `tool authorization is enabled/disabled` line. Support remedy for a client that behaves oddly or a caller reporting missing tools: set `filter_tools_list: false` and restart — authorization stays fully enforced on every tool call. ### Added
- Broker `auth.mode: oauth` (RFC 8693 token exchange, "Hop 2") is now a fully supported broker authentication mode alongside `basic` and `bearer`. A broker configured with `auth.mode: oauth` obtains its broker-bound token by exchanging the calling agent's Hop 1 token via the `broker_oauth:` block's IdP coordinates — see `docs/authentication.md` for the full Hop 1 / Hop 2 model, config shape, and operational behavior (retries, circuit breaker, `Retry-After` handling, token caching). `mcp_client_auth.mode: oauth` is required whenever any broker uses `auth.mode: oauth`, because Hop 2 consumes the agent's Hop 1 token as the RFC 8693 `subject_token`.
- New MCP tools `list-kafka-receivers`, `get-kafka-receiver-status`, `list-kafka-senders`, and `get-kafka-sender-status` for Kafka Receiver/Sender monitoring — the same list-then-drill-down pattern as `list-rdps`/`get-rdp-status` and `list-bridges`/`get-bridge-status`. A Kafka Receiver pulls messages from an external Kafka cluster into a Message VPN; a Kafka Sender pushes messages from queues in a VPN out to an external Kafka cluster. Unlike bridges' two-directional connection-state model, both objects use a single `up`/`enabled`/`failureReason` status shape (the same shape as RDPs) and a single-name identifier (`kafkaReceiverName`/`kafkaSenderName`, not a compound key). `list-kafka-receivers`/`list-kafka-senders` return up to 100 by default (max 500 via `maxResults`), with a summary block (`downCount`, `disabledCount`, `byFailureReason`); `get-kafka-receiver-status`/`get-kafka-sender-status` return additional per-object detail including topic-binding status (`topicBindingUpCount`/`topicBindingCount`) or queue-binding status (`queueBindingUpCount`/`queueBindingCount`). Read-only monitoring only; write tools and live-broker E2E fixture coverage are deferred to follow-up tickets. Unlike bridges, this implementation is spec-derived rather than lab-verified: neither lab appliance available at implementation time (one on an unreleased build, one on `sempVersion 10.26.0.8586`) exposes the `kafkaReceivers`/`kafkaSenders` SEMP paths at all, so whether `failureReason` reliably populates on a real down receiver/sender — versus staying empty the way bridges' `inboundFailureReason` did — remains unconfirmed; a follow-up should verify against a broker with the feature licensed/enabled. Tracked under SOL-152328.
- New MCP tools `list-bridges` and `get-bridge-status` for Bridge monitoring — the same list-then-drill-down pattern as `list-rdps`/`get-rdp-status`. `list-bridges` returns enabled state, inbound/outbound connection state, and last inbound failure reason for every bridge in a VPN (default 100, max 500 via `maxResults`), with a summary block (`downCount`, `disabledCount`, `byInboundFailureReason`). `get-bridge-status` returns additional per-bridge diagnostic detail — connection establisher, failure category, and client name — for one bridge, identified by `msgVpnName` + `bridgeName` + `bridgeVirtualRouter` (bridges are the only object in this server keyed by two names rather than one, because a bridge's config can differ between a broker's primary and backup virtual router in an HA pair). Tracked under SOL-152124.
- Process-level circuit breaker in front of RFC 8693 token exchange to the IdP, so a sustained IdP outage fails fast instead of driving every broker's requests into the full retry/timeout budget. One breaker per process guards the single shared IdP; because the deployment has one IdP, one client credential, and one shared availability dependency, all brokers and tenants share it. A "request" for the breaker is one complete logical exchange *after* the retry loop has finished — a chain that retries a 5xx three times before giving up records one failure, not three. Failure classification is owned by the server, not the operator: transient network errors, upstream 5xx, and response-body-read failures count toward the breaker; HTTP 429 is excluded (the IdP is reachable and throttling, so counting it would let one tenant's rate-limit trip the shared breaker); token rejections, caller cancellations, and local request-build errors are excluded (they say nothing about IdP availability). Endpoint *misconfiguration* — an untrusted/expired TLS certificate, a hostname mismatch, or a DNS name-not-found for the configured IdP — is also excluded: it is a permanent operator fault, not an outage, and counting it would let one bad config value trip the shared breaker for every tenant with no chance to heal (a DNS *timeout*, by contrast, is transient and does count). Once open, exchanges are rejected immediately with a new `ErrExchangeCircuitOpen` sentinel — classified transient like a transport failure but distinct in the audit line ("we did not try" versus retries-exhausted's "we tried and gave up"); state transitions log at WARN. Configured under a new optional `broker_oauth.circuit_breaker:` block (nested there because the breaker only protects OAuth token exchange, which exists only when `broker_oauth` does): `enabled` (default true; `false` is an operational escape hatch that disables the breaker while leaving retries intact and logs a WARN), `failure_rate_window`, `minimum_requests`, `failure_rate_threshold_percent`, `consecutive_failure_threshold` (fast-trips a fast-failing outage without waiting for the rate rule's sample; the count is window-bound, so failures spaced out by long retry chains may not accumulate; `0` disables it), `open_state_duration`, and `half_open_probe_requests`. Every field is optional and falls back to a production-safe default, so omitting the block (or the whole thing) yields the shipped defaults with the breaker on; out-of-bounds values are rejected at config load alongside every other `broker_oauth` error. The internal bucket granularity and breaker name are derived, not operator-configurable. Tracked under SOL-151600.
- Shared, process-wide backoff that honors an IdP's `Retry-After` header on an exhausted RFC 8693 token-exchange 429 chain, closing a gap in the circuit breaker's 429-exclusion policy (SOL-151600): because a 429 is deliberately excluded from breaker failure counting, and gobreaker refunds a half-open probe slot for excluded outcomes, a still-throttling IdP could previously admit unbounded sequential probes with no pacing between them. `Retry-After` is parsed per RFC 9110 §10.2.3 (both delta-seconds and HTTP-date forms; an HTTP-date at or before the current instant, or a negative delta-seconds value, floors to no gate rather than a negative one, so IdP clock skew cannot produce a nonsensical result) only when a 429 retry chain fully exhausts — not on an intermediate 429 a later retry in the same chain resolves — and only holds off *subsequent* exchange calls; it does not change the 429-excluded classification itself, nor retry pacing within a single exchange's own chain (which already honors `Retry-After` uncapped per SOL-151520 and is unaffected). The gate is shared across every broker and tenant, deliberately: it sits in front of the same one-shared-IdP circuit breaker (SOL-151600), so a 429 from one broker's exchange paces back every other caller against that IdP, not just the one that triggered it. A gated call fails fast with a new `ErrExchangeRateLimited` sentinel — distinct from `ErrExchangeCircuitOpen` so an operator (or alerting keyed on either) can tell "the IdP is unhealthy" apart from "the IdP is healthy but asked us to wait" — before any breaker bookkeeping or IdP round-trip occurs. The honored duration is capped (default 60s, double the breaker's default 30s open-state window) via a new optional `broker_oauth.retry_after:` block with a single `max_honored_duration` field; omitting the block or the field keeps the shipped default, and an operator-set value replaces it entirely in both directions (a smaller cap can clamp tighter than the default, a larger one can honor longer). Three distinct WARN log lines cover the operator-visible outcomes on every exhausted 429 chain: the gate was set (with the honored duration and expiry), the gate was set but the IdP's requested duration was clamped to the configured cap, or the gate could not be set at all because the IdP sent no `Retry-After` (or sent one that didn't parse) — the last of these is called out explicitly because it means this protection cannot engage for that IdP, distinct from a routine "everything working as intended" log line. Tracked under SOL-152285.
- Server-side retry loop for RFC 8693 token exchange to the IdP. Previously a single 5xx, HTTP 429, or connection error to the IdP failed the tool call outright; the loop now transparently retries up to three attempts total against transient signals (5xx, 429, and connection-level errors — DNS, TLS handshake, body-read partials), honoring the IdP's `Retry-After` header uncapped between attempts via jittered linear backoff. 4xx client errors (400, 401, 403) are deliberately not retried — they will not fix themselves on repeat. The whole retry loop is fenced by a chain-deadline (`context.WithTimeout` derived from the retry knobs — currently 19s worst case with the shipped defaults of 5s per attempt, 2 retries, and 1–2s backoff), which also bounds a hostile `Retry-After` value. When all attempts fail, a new `ErrExchangeRetriesExhausted` sentinel distinguishes "we tried and gave up" from a single-shot transport failure; the last attempt's HTTP status and IdP endpoint survive on the same `*ExchangeError` envelope for the audit line. JWKS refresh and OIDC discovery paths deliberately keep the non-retrying HTTP client — they are read-only lookups where a single failure is the correct signal. Tracked under SOL-151520.
- New top-level `tool_authorization:` configuration block for per-tool authorization based on the caller's group or role memberships as carried by a configurable OIDC claim. Required under `mcp_client_auth.mode: oauth` and refused under any other mode — the `enabled` field must be set explicitly to `true` or `false`, forcing every oauth deployment to make a deliberate choice on tool-level access control. When `enabled: true`, the block also carries `groups_claim_name` (name of the OIDC claim carrying the memberships; defaults to `"groups"`) and `access_level_groups` (a map from group name to the list of MCP tool names that group grants; union semantics — a caller is allowed to invoke a tool when at least one of their groups grants it). `list-brokers` is structurally exempt — every authenticated caller can invoke it regardless of the policy, so a caller can always discover configured broker aliases before invoking any other tool; listing it under a group in `access_level_groups` is inert. Authorization decisions live in a new `internal/authz` package; its `Decision` type implements `slog.LogValuer` to emit only an `allowed` flag and a matched-group count, never the group names themselves, so the sanctioned logging path cannot leak group membership. Tracked under SOL-151875, SOL-151907, and SOL-152293.

- SEMP `429 Too Many Requests` and `503 Service Unavailable` responses are now retried at most three times, independently of the configured `retries` cap (default 10). A 429/503 signals an overloaded or unavailable broker, and these retries bypass the per-broker rate limiter, so retrying up to 10 times amplified load precisely when the broker could least handle it. The cap bounds a transient episode to four requests (the original attempt plus three retries); once reached, the call fails with the same retries-exhausted error it returned before, only sooner. Other retry behavior is unchanged: the single retry for other 5xx, 401 re-authentication, connection-error retries, and the overall retry-chain deadline all still honor the full `retries` budget. ### Removed

- Per-broker `brokers.<alias>.auth.scopes` field, removed before its first release with the field populated. Rationale: scope entitlement is a property of the user (carried on the subject token), not of the broker — a single static per-broker list either hard-fails less-privileged users (strict IdPs reject `invalid_scope`) or under-scopes admins. The exchange request now omits the RFC 6749 §3.3 `scope` parameter, so the IdP grants its per-client / per-user default scopes. Config decoding is strict (`KnownFields(true)`), so any config still declaring `auth.scopes` fails loudly at startup — this is intentional and covered by a test. Follow-up SOL-151816 will design a per-user scope mechanism; if per-call scopes ever vary for the same subject token, they must also join the token-exchange dedup key (`internal/tokenexchange/dedup_key.go`).

- `broker_oauth.audience_parameter_name` no longer accepts `scope` or `resource`. Both were schema-accepted in 0.5.0 but never implemented at the wire-construction layer, so a config that passed load would have failed later — at Hop-2 runtime construction if a broker actually used `auth.mode: oauth`, or, because `broker_oauth:` is validated whenever the block is present regardless of whether any broker uses oauth mode, even a `broker_oauth:` block staged in advance with one of these values now fails at config load rather than loading cleanly. The allowlist is now `audience` only, and the rejection joins the other `broker_oauth` errors at config load. Migration: a staged `broker_oauth:` block using `scope` or `resource` must switch to `audience`; broker OAuth is not yet usable against an IdP that requires either style.

### Fixed

- The SEMP transport now bounds the TCP connection attempt, so a broker whose network path silently drops packets fails in seconds rather than minutes. Every other connection phase was already bounded — TLS handshake, response headers, expect-continue — but the dial was not, and because the transport is built as a literal rather than cloned from the default Go provides, it fell back to a dialer with no timeout. A dropped SYN, from a security group that omits the server's address range, a default-deny network policy, or a stale DNS answer after a failover, left each attempt waiting the full `semp.request_timeout_duration` while holding one of that broker's concurrency slots; because connection errors are retried, the chain could occupy a slot for roughly 15 minutes at the shipped defaults instead of about 5.5. Only calls to the affected broker are delayed — each broker has its own transport and slots, so one unreachable broker cannot stall a healthy one. The bound is derived from `request_timeout_duration` (half, capped at 10s) rather than hardcoded, so it still fires for operators who tune that value below 10s. Connections that are refused outright were already fast and are unchanged. Tracked under SOL-152403.

- OAuth broker requests now recover from an expired token in-flight. When a broker returns `401 Unauthorized` under `auth.mode: oauth`, the SEMP transport evicts the cached broker token and retries the request once with a freshly exchanged token, instead of failing the call immediately. The recovery decision belongs to the authenticator: `HandleAuthFailure` returns whether to retry and whether the retry must re-authenticate, so static modes (basic, bearer) are unaffected. The re-auth is capped at one attempt per request, so a persistently rejected credential surfaces as a `401` rather than looping. If the token exchange itself fails during the retry (for example, the IdP is unreachable), the failure is now logged with broker and operation and carries the last observed `401` status. Tracked under SOL-151624.

- `list-vpns` aggregation no longer reports a dead `zeroConnectionCount`; the count now reflects actual per-VPN connection state. Tracked under SOL-151771.

- `delete-queue-messages` and `disconnect-client` are no longer retried when a request fails in a way that leaves it unclear whether the broker already carried it out. Previously a broken connection mid-call could replay a queue purge up to 11 times, destroying messages spooled after the original request while reporting the call as failed; the retry policy inferred replay safety from the HTTP method, and SEMPv2 routes these non-idempotent actions over PUT, which RFC 9110 calls idempotent. The tools' existing `idempotent: false` annotation now drives the retry policy, and the tool result no longer tells the agent to try again — it asks it to check current state first. This holds on a transient broker status as well as a broken connection: a `429`, `503`, or other `5xx` on these two tools now surfaces as a retries-exhausted error flagged non-idempotent, carrying the "check current state first" guidance rather than the raw status. On `429` and `503` this also corrects the agent-facing `retryable` flag, which those two statuses previously set to `true` regardless of the annotation. The broker's own reason is preserved through the change, so a `503` that names a pre-execution rejection (for example, `Replication Is Standby`) still reaches the caller and still distinguishes "may have been applied" from "definitely was not". Both tools require `enable_write_tools: true`. Every other tool is unaffected, including the `config/` PUT/DELETE write tools and the `idempotent: true` actions `clear-queue-stats` and `clear-client-stats`. Tracked under SOL-152400.

- `semp.request_min_interval` now throttles a broker as a whole, as documented, instead of allowing twice the configured rate. Each protocol client built its own rate limiter, so a broker with both a SEMPv1 and a SEMPv2 client had two — and because a ticker buffers one tick, an idle protocol always had one waiting and its next request was admitted with no spacing at all. An operator setting `100ms` to protect a stressed broker was getting 20 requests/second rather than 10. Concurrency was not required to hit it: any alternation between a SEMPv1 tool (`get-broker-status`, `get-redundancy-status`, `get-discard-stats`) and a SEMPv2 tool was enough, so the exposure covered the whole tool surface. The limiter is now created once per broker and shared by both protocol clients, matching how the in-flight cap `semp.max_concurrent_per_broker` was fixed in SOL-150116, and it is stopped in one place when the broker client closes. The default is `100ms`, so this applies to every deployment that has not disabled throttling. Tracked under SOL-152401.

### Security

- `Token` and `Exchange` types now implement `LogValue`/`String`/`GoString` guards so raw OAuth tokens cannot leak through `slog`, `fmt`, or `%#v` rendering. Tracked under SOL-151649.
- SEMPv2 path-parameter values are now rejected before URL construction when they are empty or a dot segment (`.` or `..`). `buildURL` escaped `/` but left dot segments intact, so a value like `..` could, on a broker or fronting proxy that normalizes dot segments, collapse a request onto an unintended (for example, parent) path — most consequentially on the destructive `config/deleteMsgVpn`, `config/deleteMsgVpnQueue`, and `action/doMsgVpnQueueDeleteMsgs` operations. The guard rejects the value with a clear error naming the parameter and covers read and destructive operations at the single substitution choke point. Tracked under SOL-152208.

- `listen_address` server config with a loopback-only default, so the server does not bind a public interface unless explicitly configured. Tracked under SOL-150690.
- RFC 8693 OAuth token-exchange runtime (broker-OAuth "Hop 2"), gated behind `ENABLE_UNRELEASED_BROKER_OAUTH`. Tracked under SOL-150799, SOL-150800, SOL-150801.
- Aggregations for `list-vpns`, `list-rdps`, `list-slow-subscribers`, `list-queue-discards`, and `get-rdp-status`. Tracked under SOL-151313, SOL-151314, SOL-151315, SOL-151316, SOL-151343.
- Accurate live queue-depth reporting. Tracked under SOL-150260.
- New top-level `broker_oauth:` configuration block for upcoming OAuth authentication from the MCP server to brokers. Schema-only in this release — the OAuth runtime is not yet wired, and any broker with `auth.mode: oauth` is rejected at startup with a standalone error banner explaining the limitation and a per-broker validation error in the joined config error. The block holds the global IdP coordinates the MCP server will use to obtain broker-bound tokens: `idp_token_endpoint`, `mcp_server_client_id`, an `mcp_server_client_auth` discriminated union (one named sub-block per IANA "OAuth Token Endpoint Authentication Methods" identifier — V1 supports `client_secret_basic` and `client_secret_post`), `grant_type` (allowlisted to RFC 8693's token-exchange URN), and `audience_parameter_name` (allowlisted to `audience` | `scope` | `resource`). The discriminated-union shape structurally prevents misconfigured method/credential pairings — operators select a method by populating its named sub-block; the validator enforces "exactly one sub-block populated." Per-broker `auth.mode: oauth` accepts an optional `audience` field whose value is forwarded to the IdP when set. The validator also enforces a permanent structural invariant: if any broker uses `auth.mode: oauth`, `mcp_client_auth.mode` must also be `oauth` (the MCP server cannot obtain a broker token without the agent's token from the client-auth side). Operator-facing banners and errors live in a new `internal/banner` package so future banners land in one canonical home. Tracked under SOL-150796.

### Changed

- **BREAKING**: Top-level client-authentication block renamed from `client_auth:` to `mcp_client_auth:`. The Go type renames to `MCPClientAuthConfig`, and the field on `ServerConfig` renames to `MCPClientAuth`. The rename disambiguates the operator-facing schema now that the new `broker_oauth:` block introduces a separate `broker_oauth.mcp_server_client_auth:` nested sub-block — the top-level `client_auth:` name was ambiguous between client authentication on the inbound side (agents authenticating to the MCP server) and on the outbound side (the MCP server authenticating to the IdP). Migration: rename the top-level `client_auth:` key in every config to `mcp_client_auth:`. No field semantics change; only the block name. Tracked under SOL-150796.

- **BREAKING**: A broker configured with `insecure_skip_verify: true` is now refused at startup under `mcp_client_auth.mode: oauth` (production), unless a new top-level `allow_insecure_broker_tls: true` opt-in is also set. Previously this combination started successfully with only a `slog.Warn`, leaving TLS certificate verification disabled while the server still sent the broker admin credential over the connection on every SEMP request — an exploitable man-in-the-middle path. Mirrors the existing `allow_remote_unauthenticated` guard. `allow_insecure_broker_tls` is server-wide, not per-broker: it lifts the check for every broker in the config, not just the one being onboarded. Dev/static modes are unchanged and continue to allow self-signed brokers without the opt-in. Migration: add `allow_insecure_broker_tls: true` to accept the risk, or install a trusted certificate on the broker. Tracked under SOL-151517.

- Validator now trims whitespace before checking emptiness for basic-auth `username`/`password` and bearer-auth `token`. Configs whose credentials resolve to a whitespace-only string (for example, `token: " "` or a `${VAR}` substitution that yields only whitespace) are now rejected at startup with a clear "required for X auth" error rather than passing validation and failing every SEMP request with a 401 at runtime. Tracked under SOL-150796.

- Lifted `SafeCookieJar` to the broker level and delegated 401 recovery to the `Authenticator`. Tracked under SOL-151468.
- Unified `downCount` semantics across the `list-*` aggregating tools. Tracked under SOL-151552.

### Fixed
- Bound broker-controlled error text at capture, so an oversized broker error can't blow up memory or logs. Tracked under SOL-151516.
- Recover panics in `errgroup` worker goroutines instead of crashing the server. Tracked under SOL-151514.
- Bound the overall SEMP retry chain with a deadline. Tracked under SOL-151518.

## [0.3.0] - 2026-06-03

### Added
- Per-invocation caller identity on tool-invocation log lines (`sub`, `iss`, `client_id`, `jti`) in `oauth` and `static` client-auth modes. Missing optional claims surface as the `<absent>` sentinel so log consumers see a stable schema; `disabled` mode emits no identity fields. Tracked under SOL-149606.
- Basic health endpoints. Tracked under SOL-148426.
- Advanced monitoring tools: replication, discards, and slow subscribers. Tracked under SOL-148432.

### Changed

- **BREAKING**: Client auth config consolidated into single required `client_auth.mode` enum (`disabled` | `static` | `oauth`). The legacy `development_mode` flag is deprecated and ignored — its presence in YAML logs a deprecation warning at startup. The previous "development_mode + empty dev_token = silent no-auth" path (SOL-149921) is replaced by the explicit `mode: disabled`. Migration:

  | Old config | New config |
  |---|---|
  | `development_mode: true` + `dev_token: "abc"` | `client_auth: { mode: static, dev_token: "abc" }` |
  | `development_mode: true` + missing/empty `dev_token` | `client_auth: { mode: disabled }` |
  | `development_mode: false` + OIDC fields | `client_auth: { mode: oauth, issuer, audience, resource_url }` |

  `mode: oauth` is the only legal production mode and enforces `https://` on broker URLs, issuer, and resource_url. `mode: disabled` and `mode: static` are development-only and allow `http://`. A prominent WARN-level boot banner fires for `disabled` and `static` modes. Tracked under SOL-149989.

- **BREAKING**: Broker aliases must now satisfy a contract: 1–63 characters, only letters/digits/hyphens, must start and end alphanumeric, compared case-insensitively. Configs that previously loaded silently will now be rejected at startup if they contain: empty aliases, whitespace, underscores, dots, embedded special characters, leading or trailing hyphens, aliases longer than 63 characters, or case-only collisions (for example, `Prod` and `prod` in the same config). Original casing is preserved in all user-facing output (logs, `list-brokers`, error messages); tool calls resolve case-insensitively so any casing of a configured alias works. Migration:

  | Old alias | New alias |
  |---|---|
  | `prod_east` | `prod-east` |
  | `Prod` + `prod` (collision) | rename one of them |

  Tracked under SOL-149789.

- `ToolManager.CallTool` now takes a trailing `Identity` argument carrying per-invocation audit identity. This is an internal Go API (the package is `internal/tools`); on-the-wire MCP tool schemas and operator-visible config are unchanged. Tracked under SOL-149606.

- Config loader now rejects unknown YAML fields at startup instead of silently ignoring them. Previously, a typo like `developmnet_mode` or `insecure_skip_verfy` was accepted and the operator's intended override became a no-op. The loader now fails fast with an error naming the offending field. Existing configs with stale or misspelled keys will fail to start until the typo is corrected; configs with only valid keys are unaffected. Tracked under SOL-149927.

- Skip environment-variable substitution inside YAML comments. Tracked under SOL-149904.

### Deprecated
- The `development_mode` config flag is deprecated in favor of `client_auth.mode` (see the consolidation entry under Changed). It is still parsed but ignored, and logs a deprecation warning at startup. Tracked under SOL-149989.

### Removed
- **BREAKING**: `get-dmr-status` tool removed. Migration: clients invoking `get-dmr-status` must stop; DMR state is available through the remaining monitoring tools. Tracked under SOL-150316.

### Fixed
- OIDC token verifier now bounds the HTTP client used by go-oidc for both startup discovery and lazy JWKS refresh (10s per-request timeout). Previously, the verifier fell back to `http.DefaultClient` (zero timeout), and a slow or hung identity provider during key rotation could wedge the JWKS-refresh goroutine indefinitely and stall per-request token verification past the inbound MCP request's own server-side deadlines. The existing 30s discovery deadline is preserved. Operators running an IdP that legitimately takes longer than 10s to serve `/jwks` will see auth fail closed; document the timeout if your environment requires tuning. Tracked under SOL-150219.
- Wrap the cookie jar in an atomic `SafeCookieJar` to remove a 401 race. Tracked under SOL-149922.
- Cap broker response body at 16 MiB. Tracked under SOL-149920.
- Set granular timeouts on the SEMP HTTP transport, and `ReadTimeout`/`IdleTimeout` on the MCP HTTP server. Tracked under SOL-149925 and SOL-149914.
- Close the broker pool on graceful shutdown. Tracked under SOL-149926.

### Security
- Redact userinfo credentials in broker-URL validation errors. Tracked under SOL-149923.
- Warn on `insecure_skip_verify: true` in production mode. Tracked under SOL-149928.

This project uses [Semantic Versioning](https://semver.org/):
- **MAJOR** version for incompatible API changes

1. Update this CHANGELOG with all changes in `[Unreleased]`
